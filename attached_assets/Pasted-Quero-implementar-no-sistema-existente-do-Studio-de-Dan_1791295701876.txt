Quero implementar no sistema existente do **Studio de Dança Classe A** uma funcionalidade de **Matrícula Online Pública**, permitindo que pais ou responsáveis realizem a solicitação de matrícula de suas filhas pelo celular, SEM necessidade de criar login e senha.

IMPORTANTE: o sistema já está funcionando e possui cadastro de alunas, responsáveis, turmas e demais funcionalidades administrativas.

NÃO quero recriar o cadastro atual.

A nova funcionalidade deve aproveitar ao máximo a estrutura, regras, componentes, validações e dados que já existem.

## 1. ANTES DE IMPLEMENTAR

Primeiro analise o projeto atual e identifique:

- Como funciona atualmente o cadastro/matrícula de uma aluna.
- Quais tabelas e entidades participam desse processo.
- Quais campos existem para aluna.
- Quais campos existem para responsável.
- Como funciona a associação entre responsável e aluna.
- Como funciona a associação entre aluna e turma.
- Quais campos são obrigatórios.
- Quais validações já existem.
- Quais campos são administrativos/internos.
- Como funciona atualmente a criação de matrícula.
- Como são tratados status de matrícula/aluna.
- Se já existe conceito de matrícula pendente, pré-matrícula ou equivalente.
- Como funciona a autenticação e autorização das APIs.

Somente depois dessa análise implemente a solução.

Priorize reutilizar a arquitetura existente.

NÃO crie tabelas duplicadas se a estrutura atual puder ser reutilizada com segurança.

Caso seja necessária alteração de banco de dados, faça somente a alteração mínima necessária e explique ao final o que foi criado/modificado.

## 2. OBJETIVO

Criar uma página pública de matrícula, acessível SEM LOGIN.

Exemplo de rota:

/matricula

Essa rota deverá poder ser acessada diretamente pelo navegador do celular.

IMPORTANTE:

Somente essa funcionalidade deve ser pública.

NÃO remover autenticação das telas administrativas.

NÃO permitir que usuários não autenticados acessem:

- lista de alunas;
- dados de outras alunas;
- responsáveis cadastrados;
- pagamentos;
- mensalidades;
- dashboard;
- turmas administrativas;
- usuários;
- relatórios;
- configurações;
- qualquer outra informação interna.

A rota pública deverá permitir somente:

1. carregar as informações estritamente necessárias ao formulário;
2. enviar uma nova solicitação de matrícula.

## 3. EXPERIÊNCIA MOBILE-FIRST

A página deverá ser criada pensando principalmente no celular.

Quero uma aparência elegante, simples e profissional, mantendo a identidade visual do Studio Classe A:

- preto;
- rosa;
- branco;
- identidade relacionada ao ballet;
- layout delicado e moderno.

A página deverá ser totalmente responsiva.

No topo:

Logo/identidade do Studio Classe A

Título:

"Matrícula Online"

Texto:

"Preencha os dados abaixo para solicitar a matrícula. Após o envio, o Studio Classe A analisará as informações e entrará em contato para confirmação."

## 4. FORMULÁRIO

NÃO invente inicialmente um conjunto completamente novo de campos.

Analise o formulário de cadastro/matrícula existente e reaproveite os campos adequados para preenchimento pelo responsável.

Separe visualmente o formulário em etapas ou seções para facilitar o preenchimento pelo celular.

Sugestão:

### Etapa 1 — Dados da aluna

Utilizar os campos existentes adequados, como por exemplo:

- Nome completo
- Data de nascimento
- CPF, se aplicável
- demais dados pessoais que já sejam necessários no cadastro atual

### Etapa 2 — Dados do responsável

Utilizar os campos existentes adequados, como:

- Nome do responsável
- CPF
- Telefone/WhatsApp
- E-mail
- Grau de parentesco

Utilize somente campos que façam sentido de acordo com o modelo atual do sistema.

### Etapa 3 — Endereço

Se o sistema atualmente utiliza endereço no cadastro, permitir o preenchimento dos campos necessários.

Caso exista integração/consulta de CEP, reutilize-a.

### Etapa 4 — Interesse na matrícula

Permitir informar a modalidade/turma pretendida somente se isso puder ser feito de maneira segura utilizando a estrutura atual.

Se as turmas puderem ser apresentadas publicamente, a API pública deverá retornar SOMENTE informações necessárias para seleção, como:

- nome;
- modalidade;
- faixa etária, se existir;
- dias;
- horários;
- vagas, somente se essa informação já existir e for apropriada.

NÃO expor IDs internos desnecessariamente ou outras informações administrativas.

Caso seja melhor para a arquitetura atual, permitir apenas "Turma/Modalidade de interesse", deixando a definição final para o Studio.

### Etapa 5 — Informações adicionais

Reaproveitar informações relevantes existentes no cadastro atual que façam sentido para os responsáveis preencherem.

NÃO mostrar campos administrativos ou internos.

## 5. NÃO EFETIVAR A MATRÍCULA AUTOMATICAMENTE

Este requisito é muito importante.

O envio do formulário público NÃO deve transformar automaticamente a pessoa em uma aluna matriculada/ativa, a menos que a arquitetura existente exija outra abordagem e isso seja claramente explicado antes.

O fluxo desejado é:

Responsável preenche formulário
→
Solicitação recebida
→
Status "Pendente de aprovação"
→
Studio analisa
→
Studio aprova
→
Matrícula/aluna é efetivada

Criar ou reutilizar um status equivalente a:

PENDENTE_APROVACAO

Não incluir automaticamente essa matrícula nos indicadores de alunas ativas caso isso distorça os números atuais.

## 7. APROVAÇÃO

Ao selecionar "Aprovar matrícula":

Reutilizar o processo de cadastro/matrícula já existente no sistema.

NÃO criar um segundo processo paralelo se o sistema atual já possui regras para criar aluna, responsável e matrícula.

A aprovação deve:

- validar os dados;
- verificar duplicidades;
- aproveitar responsável existente quando apropriado;
- criar/atualizar a aluna conforme as regras atuais;
- criar a matrícula;
- associar turma quando aplicável;
- manter integridade dos relacionamentos;
- registrar que a origem foi "Matrícula Online", se isso puder ser implementado de forma simples e útil.

Antes de efetivar, mostrar confirmação ao usuário administrativo.

## 8. PREVENÇÃO DE DUPLICIDADE

Antes da aprovação, verificar possíveis registros existentes.

Utilizar principalmente identificadores confiáveis existentes no sistema, como CPF da aluna e/ou CPF do responsável, conforme o modelo atual.

Também poderá utilizar e-mail/telefone como alerta secundário, mas NÃO considere duas pessoas automaticamente iguais apenas porque possuem telefone ou e-mail semelhante.

Caso exista possível duplicidade, NÃO criar automaticamente outro registro.

Mostrar ao administrador algo como:

"Encontramos um possível cadastro existente."

Permitir analisar antes de continuar.

## 9. REJEIÇÃO

Ao rejeitar uma solicitação:

Solicitar confirmação.

Se possível, permitir registrar um motivo interno opcional.

Alterar o status para:

REJEITADA

Não excluir imediatamente os dados da solicitação.

Registrar data da decisão.
